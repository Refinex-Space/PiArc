# 0037. 权限规则、Bash 命令分析与模式的落地（补充）

- 状态：已接受，补充 ADR-0004、ADR-0005、ADR-0031
- 日期：2026-11-18
- 相关：架构第 6.2、7.4、9.2、10.3 节；T23

## 背景

T23 要让 Claude Code 格式的规则在 PiArc 中按同样语义生效，复合命令逐段判定，并补上计划与跳过权限两种模式。架构第 6.2 节给出了规则形式、求值顺序和裁决阶梯，没有规定以下细节：无效规则怎么处理、命令里的运行期值怎么匹配、只读白名单靠什么防止工作区里的同名程序、"总是允许"如何携带多条规则、Agent Host 怎样知道哪些工具被整体拒绝、跳过权限从哪里开启。

## 决策

1. **无效规则不被静默丢弃。** allow 规则解析失败时忽略并报告；deny 或 ask 规则解析失败时，按更严格的语义处理：它点名的工具（读不出名字时为所有工具）的每次调用都询问。设置页和审计都列出这些规则与原因。
2. **运行期值保守匹配。** 命令中由变量、命令替换等决定的部分记作占位符。allow 规则必须对所有取值成立；deny 规则只可能命中时询问；ask 规则可能命中即询问。解析失败、`eval`、命令名是运行期值、`sh -c` 的脚本是运行期值的命令一律询问，跳过权限也不例外：这时无法确认 deny 规则与关键路径删除。
3. **exec 包装与影子命令。** `sudo`、带选项的 `env` 与 `xargs`、`watch`、`find -exec`、`sh -c` 等运行其他程序的命令只能被精确规则允许；它们运行的命令作为影子命令参与 deny、ask 与关键路径检查。命令以路径给出时（`/bin/rm`），deny 与 ask 也按程序名检查。
4. **自动允许依赖的程序在执行时钉住。** 只读白名单与 Accept edits 的文件命令自动放行时，Core 按命令环境的 PATH 解析每个外部程序（PATH 不能指向工作区，程序不能位于会话可写目录；文件命令必须是系统工具；Windows 只接受 Git 安装内经探测确认的程序），执行前由 bash 启动文件核对实际解析结果并钉住，路径操作数在执行前再按同一 scope 检查一次。ADR-0031 第 3 条只覆盖四个文件命令的做法推广到全部自动允许的程序。
5. **"总是允许"携带规则列表。** 审批卡与答复的 `rule` 改为 `rules`（每个仍需批准的子命令一条前缀规则，至多 5 条，用户可逐行编辑）；原生确认框列出全部规则；Core 逐条校验为合法的 allow 规则再写入 `.piarc/settings.local.json`。"本会话允许"记住同一组规则。关键路径删除、无法判定、修改命令解析环境或命中 ask 规则时不提供"总是允许"。
6. **整体拒绝的工具由 Core 判定、Agent Host 移除。** 新增 AHP 请求 `policy/tools`：Agent Host 每次运行前把当前工具的规范名交给 Core，Core 返回被不带 specifier 的 deny 规则覆盖的工具，Agent Host 用 Pi 1.5.2 的 `setActiveTools` 把它们移出本次请求，规则撤销后恢复。请求失败时保持原列表，每次调用仍经 `policy/evaluate`。
7. **跳过权限只能由用户开启。** 开关是用户级设置 `permissions.enableBypassPermissions`（项目文件设置无效）。Core 拒绝未开启时切换到该模式；主进程在切换前弹原生确认。项目配置中的 `bypassPermissions` 与 `auto` 不生效，每次会话起始时写入审计。所选模式记入 `workspaces.default_mode`，新会话按"会话显式 → 工作区记忆 → 设置 → 手动"取起始模式，记忆的跳过权限只在开关仍开启时恢复。
8. **PowerShell 不拆分。** 整条匹配且不区分大小写；带 `*` 的 allow 规则只在命令不含语句分隔、管道、子表达式等字符时生效，否则需要精确规则；deny 与 ask 规则另对按分隔符粗分的片段检查，命中时只询问。
9. **审计记录命中的规则与来源。** 每次裁决写入步骤、命中规则、来源层与结论。不含通配的 Bash、PowerShell 规则可能内嵌凭据，审计只存其摘要。设置页按会话、工具、结论与时间筛选。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 无效 deny 规则按整体拒绝该工具 | 最严格 | 一条笔误就让工具不可用，用户难以发现原因 | 否决，改为询问并报告 |
| 无效 deny 规则直接忽略（Claude Code 的做法） | 简单 | 用户以为生效的拦截静默失效 | 否决 |
| 只读命令不核对实际程序 | 实现简单 | PATH 中的工作区目录或同名脚本可在手动模式下不经审批执行 | 否决 |
| 保留单条 `rule` 字段，用换行拼接多条规则 | 不改协议 | 字段含义含糊，原生确认与校验都要再拆分 | 否决 |
| 由 Agent Host 读取设置判断整体拒绝 | 少一次往返 | 规则解释分散到两处，违反 ADR-0004 第 1 条 | 否决 |

## 后果

- 正面：规则语义与 Claude Code 一致；复合命令中任一段的 deny 或 ask 都会生效；只读命令在手动模式下免审批且不会被工作区程序冒名；整体拒绝的工具不再出现在模型请求里。
- 负面与代价：每次回合开始多一次 AHP 往返；自动允许依赖 PATH 解析，用户 shell 自定义了命令解析（`BASH_ENV`、导出函数、`DYLD_*` 等）时只读命令也要询问；Windows 的程序探测只能在 CI 与 W1 实测。
- 需要配套做的事：T25 用 `PolicyHooks` 填入两个插槽；T24 加入 `.claude/` 两层时给出它们的锚点目录；T31 评估 `Agent(model:…)` 一类参数规则；M4 评估 PowerShell 的语法级拆分与别名。

## 重新评估的触发条件

- Claude Code 的规则语法或复合命令处理发生不兼容变化；
- tree-sitter-bash 升级改变节点类型；
- 自动裁决 p95 超过 2 ms。
