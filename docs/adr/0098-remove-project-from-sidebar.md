# 0098. 从侧栏移除项目

- 状态：已接受（补充）
- 日期：2026-11-27
- 取代：无
- 相关：架构文档第 9.2 节（`workspaces`）、第 7.6 节（实体快照）、第 10.3 节（原生确认）；ADR-0029、ADR-0049、ADR-0052

## 背景

侧栏的项目组来自 Core 的 `workspaces` 表，加上会话索引里的 `workspace_path`：没有工作区行的会话也会以目录名单独成组。用户没有办法把不再使用的项目从侧栏拿掉。`closeWorkspace` 只停 Agent Host，记录还在；只删工作区行，项目会带着会话重新出现，还会丢掉该项目记住的默认模式与模型。

参考产品的做法：ChatGPT 桌面端（Codex）项目菜单的 Remove 把项目从侧栏移除，重新添加文件夹即恢复；Claude Desktop 的 Archive project 写明"任务、定时任务和文件不会被删除"。两者都不删除会话与文件。

## 决策

1. "移除项目"只把项目移出列表，不删除文件夹、会话文件、会话索引与该项目记住的设置。
2. `workspaces` 增加 `removed` 列（schema v15）。`Store::workspaces` 不列出已移除的行；`remove_workspace` 标记该行，路径没有行时插入一条已标记的行，使只有会话的组同样消失。
3. Core 的 `Hub::remove_workspace` 先停止该工作区的后台任务（`TaskManager::workspace_removed`，状态记为 `killed`，输出与记录保留），再关闭其会话与 Agent Host，最后标记。快照任务读取已移除的路径，`core/workspaces` 与 `core/sessions` 都不列出它们与它们的会话（按会话的 `workspace`，没有时按 `cwd`）。
4. 只有用户明确打开才恢复：`openWorkspace`（打开文件夹、拖入、`piarc://open`）与在该项目中新建会话会清除标记并重新列出。其他请求（恢复会话、模型与命令列表、MCP 状态等）遇到已移除的工作区一律拒绝，不恢复也不启动 Agent Host。移除进行期间任何打开请求都被拒绝：否则窗口恢复刚被关闭的会话会抢在标记之前重新登记工作区，项目留在后台、再也列不出来。
5. 主进程的 `removeWorkspace` 先向 Core 取该工作区运行中的会话与后台任务数（`workspaceWork`）；有运行中的工作时弹原生确认并写明数量，用户取消就什么都不做。没有运行中的工作时直接移除，因为这个操作可以撤回。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 归档全部会话并删除工作区行 | 沿用已有归档 | 结束后台命令、worktree 逐个询问；"显示已归档"时项目以目录名回来；丢掉默认模式与模型 | 不采用 |
| 删除全部会话与记录 | 彻底 | 不可恢复，参考产品都不这样做 | 不采用 |
| 只在渲染进程的布局里隐藏 | 不动 Core | 只对一个窗口生效；Core 的设置页仍列出它；运行中的工作无人处理 | 不采用 |

## 后果

- 正面：可撤回；重新打开文件夹即回到原样；设置页的工作区选择与快照用同一份列表。
- 负面与代价：只有会话、没有工作区行的路径也会留下一条标记行。
- 需要配套做的事：Store 迁移与单测；Core 的会话层端到端（移除、恢复、删除了的文件夹、移除期间的恢复请求）；主进程单测；L4 `workspace-remove.e2e.ts`；preload 白名单与 S10 报告。

## 重新评估的触发条件

- 需要在应用内列出并恢复已移除的项目（例如"最近移除"）。
