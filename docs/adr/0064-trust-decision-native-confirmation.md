# 0064. "信任"项目的决定经主进程原生确认

- 状态：提议
- 日期：2026-11-22
- 修订：ADR-0029 备选方案中"信任决定也在主进程弹原生确认框：暂不做"一行；架构第 10.2 节 T18 落地一段的"信任决定由渲染进程发出、没有原生确认"
- 相关：I79（T18 登记、T45 评估后交 R5）；R5 安全审查 S3；架构第 10.1 节"渲染进程注入（XSS）"与"恶意项目配置"两行、第 10.3 节 preload 与 IPC；[ADR-0029](0029-client-shell-foundations.md)、[ADR-0034](0034-bind-read-and-trust-confirmation.md)、[ADR-0058](0058-plugins-pi-packages-and-mcp-prompts.md)、[ADR-0062](0062-security-hardening-threat-map-redaction-and-diagnostics.md)

## 背景

项目信任是第 10.2 节的闸门：信任之前，项目的 hooks、MCP server、allow 规则、插件与 Pi 扩展都不生效。信任决定由渲染进程经 `window.piarc.decideProjectTrust(dir, true, version)` 发给主进程，主进程校验参数后直接交给 Core（`apps/desktop/src/main/core/session-ipc.ts` 的 `trustDecide`），没有原生确认。

其他能放宽"什么可以不经用户运行"的命令都经主进程原生确认：

| 命令 | 原生确认 | 来源 |
|---|---|---|
| 新增或修改 allow 规则 | 有 | T23，第 10.3 节 |
| 审批卡的"总是允许" | 有 | T20 |
| 切换到跳过权限模式 | 有 | T23 |
| 开启插件、允许插件新增的可执行项 | 有（`NativeConfirm`，列出来源与每项） | T40，ADR-0058 |
| 沙箱的自动批准、新增域名、关闭沙箱、删减 `denyRead` | 有 | T39，R5 |
| 删除会话 | 有 | T18 |
| **信任项目** | **无** | T18 |

信任比上表任何一项放开得都多：一次决定让项目的全部 hooks（Core 在沙箱外运行的命令）、MCP server 与 allow 规则同时生效。T45 评估（I79）时的残余风险是：渲染进程被注入后，页面可以先 `trustGet(dir)` 取得清单版本，再 `trustDecide(dir, true, version)`，用户什么都看不到。现有防线是渲染进程加固（CSP、不从 HTML 建 DOM、XSS 载荷在全部渲染面的回归、畸形 IPC 参数测试），它们降低了注入的可能，但不改变"注入之后能静默信任"这一点。R5 的独立安全审查（S3）得出同样结论。

ADR-0029 当时没有做，理由是"用户要连点两次；审批卡同样在渲染进程作答"。审批卡在渲染进程作答只影响一次调用；信任影响项目今后的全部可执行配置，量级不同。

## 决策

1. "信任"（`trusted: true`）的决定由主进程弹原生确认框后才交给 Core：标题说明将启用项目的可执行配置，正文按类别列出将生效的项与数量（hooks、MCP server、allow 规则、插件与扩展、子 agent 与 skill 的可执行项），取自 Core 的信任视图（与渲染进程的信任对话框同一份清单与版本，ADR-0034）；项名超过一行时截断并显示双向控制字符（与审批卡同一处理）。用户取消时答 `cancelled`，不改变决定。
2. "暂不信任"（`trusted: false`）与撤销信任不需要原生确认：它们只收紧。
3. 用户在渲染进程的信任对话框里点"信任"之后，原生确认是第二步。为不让用户对同一件事回答两次，渲染进程的信任对话框保留清单与说明，"信任"按钮直接触发原生确认（对话框本身不再有"确认"一步）。
4. L4：`t45-ipc-hardening` 的伪造用例加入 `decideProjectTrust(dir, true, version)` 并断言停在原生确认；`t18-trust` 等用例用现有的 `stubMessageBox` 代答。威胁映射 THR-02、THR-11 各加一行。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. "信任"经原生确认，信任对话框直接触发它（本决策） | 与 allow 规则、插件、沙箱放宽一致；注入的页面不能静默信任 | 首次信任一个项目多出一个系统对话框 | 推荐 |
| B. 维持现状，靠渲染进程加固 | 首次使用少一步 | 渲染进程被注入时能静默启用项目的全部可执行配置（I79 的残余风险） | 不采纳 |
| C. 只在项目有可执行项时才原生确认 | 没有 hooks、MCP、规则的项目不多一步 | 判断"有没有"在 Core 的视图里，与 A 的实现成本相同；没有可执行项时信任本来没有效果，多一步无妨 | 可作为 A 的细化：清单为空时不弹 |
| D. 信任决定移到主进程的原生窗口里完成（不经渲染进程） | 渲染进程完全不参与 | 要在原生对话框里展示分类清单与说明，系统对话框的排版能力不够；与现有信任对话框重复 | 不采纳 |

## 后果

- 正面：第 10.1 节"渲染进程注入"与"恶意项目配置"两行之间的缺口关闭；信任与其他放宽操作的确认方式一致。
- 负面与代价：第一次在一个有可执行配置的项目里开会话时多一个系统对话框；信任对话框的交互要改（第 3 条）；L4 中做出信任决定的用例都要代答原生确认。
- 需要配套做的事（采纳后）：
  - 主进程 `trustDecide` 先取 Core 的信任视图、弹确认，取消时答 `cancelled`；渲染进程的信任对话框处理 `cancelled`（保持打开）。
  - 架构第 10.2 节 T18 一段、第 10.3 节 preload 与 IPC、ADR-0029 状态注明第 N 条被本 ADR 修订；`tests/security/threats.yaml` 与 `docs/security/threat-coverage.md`。
  - 由 M5 的第一个任务（T46 之前或随 T46）实现，或单独排一个小任务；用户决定时一并指定。

## 重新评估的触发条件

出现以下任一情况时复核本决策：

- 用户反馈首次信任的额外确认成为主要摩擦（例如每个新克隆的仓库都有可执行配置）。
- 渲染进程与主进程之间有了不依赖渲染进程的确认通道（例如系统级的安全输入），可以替代原生对话框。
