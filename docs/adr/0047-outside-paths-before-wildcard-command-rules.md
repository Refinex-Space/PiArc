# 0047. 越界路径的询问先于带通配的命令 allow 规则

- 状态：提议，修订 ADR-0037 中裁决阶梯第 6、7 步的顺序
- 日期：2026-11-20
- 相关：架构第 6.2.3、10.1 节；ADR-0031、ADR-0037、ADR-0046；登记事项 I116；R3

## 背景

架构第 6.2.3 节与 ADR-0037 的阶梯中，allow 规则（第 6 步）先于"越界 → 询问"（第 7 步）。命令的 allow 规则只匹配命令文本：`Bash(sed *)`、`Bash(awk *)` 这类带通配的规则同时放行了它们读写工作区外的路径。T30 的 L3 比对（`perm-compound` 的 `outside` 调用）记录了与 Claude Code 2.1.318 的差异：同样有 `Bash(awk *)`，`awk … ../outside.txt` 在 Claude Code 中询问，在 PiArc 中直接运行。

这条差异在 PiArc 中的影响比在规则手写时更大："总是允许"按程序名或子命令生成前缀规则（ADR-0037 第 5 条；`rm`、`cp`、`mv` 等只给精确规则），用户批准一次 `sed -i … notes.txt` 得到 `Bash(sed *)`，之后 `sed -i … ~/.ssh/config` 也不再询问。受保护路径（第 5b 步）只覆盖 `.git/`、`.piarc/`、`.claude/`、`.pi/` 与 shell 配置文件，`~/.ssh/`、`~/.aws/` 之类不在其中。第 10.1 节的第一条威胁"提示注入导致破坏性操作"的对策是默认询问与子命令分析，这里正是 allow 规则把分析得出的越界结果丢掉了。

## 决策

1. Bash 与 PowerShell 的调用里，Core 分析出越界路径（读或写会话目录之外）时，**带通配的** allow 规则不在第 6 步放行，调用继续到第 7 步并因越界而询问。
2. 不带通配、与整条命令逐字相同的 allow 规则（例如 `Bash(cat /etc/hosts)`）照旧在第 6 步放行：用户写下的就是这条命令和它的路径。
3. 文件工具（Read、Edit、Write、Glob、Grep、NotebookEdit）的路径规则不变：规则本身写的是路径，命中即说明用户允许了该位置。
4. PreToolUse hook 的 allow 不变（跳到第 6 步，不越过第 3、4、5 步，ADR-0039），只读白名单的判断不变（它本来就要求路径在会话目录内）。
5. 审批卡沿用越界询问的说明；"总是允许"对这类调用仍按前缀生成规则，规则保存后同类越界调用继续询问。
6. 实现位置：`piarc_policy::decide` 的第 6 步增加"命令规则命中且全部为精确规则，或没有越界"的条件；`Input` 增加区分精确与通配命中的事实，由 `tool_io::policy::assess` 填入；`tests/bash_cases.json` 与 L2 `perm-bash-compound` 增加越界用例；L3 `perm-compound` 的 `outside` 两条 allowlist 条目删除。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 维持现状，allowlist 写明理由 | 不改阶梯 | 一次"总是允许"即可让同类命令无询问地写工作区外的任意文件 | 否决 |
| 越界检查整体移到第 6 步之前，对所有工具生效 | 规则简单 | 文件工具写明外部路径的 allow 规则失去作用，`additionalDirectories` 之外的常用外部读取每次都问 | 否决 |
| 扩大受保护路径清单 | 不改阶梯 | 清单永远列不全，且只覆盖写入 | 否决 |

## 后果

- 依赖 `Bash(<命令> *)` 读写工作区外文件的用户会看到新的询问；要免询问需写精确规则，或把目录加入 `additionalDirectories`。
- 与 Claude Code 2.1.318 在 L3 `perm-compound` 上的这条差异消失。
- 阶梯的步骤名不变（越界仍记为 `outsideWorkspace`），审计可以区分。

## 重新评估的触发条件

- Claude Code 改变越界路径与 allow 规则的先后（L3 Nightly 会报告新的差异）。
- 用户反馈精确规则不足以表达常用的外部路径操作。
