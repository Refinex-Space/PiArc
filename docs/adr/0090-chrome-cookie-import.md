# 0090. 从 Chrome 导入登录与浏览器分区里的凭据

- 状态：已接受（2026-11-26 用户确认）
- 日期：2026-11-26
- 修订：ADR-0021"凭据只存在 Core 的保险箱"（浏览器分区的 cookie 例外）
- 相关：ADR-0062（脱敏）、ADR-0088、ADR-0089；[设计增补 B5](../architecture/addenda/browser.md)

## 背景

内置浏览器的每个工作区有一个持久分区，用户在面板里登录本地应用后，智能体复用这份登录测试受保护页面。用户还要求能从本机 Chrome 导入登录（听过风险后坚持）。分区里的 cookie 与导入的 cookie 都是凭据，但它们存在 Chromium 的分区存储里，不在保险箱；导入还需要读取 Chrome 的加密密钥。

## 决策

1. **分区 cookie 是 ADR-0021 的例外。** 浏览器分区的 cookie、存储与 HTTP 缓存由 Chromium 管理（`EnableCookieEncryption` fuse 已开），不进保险箱，也不进 Core 的日志、审计与诊断包。设置页提供"退出即清空"模式与"清除本工作区浏览数据"。
2. **导入只按站点、只由用户发起。** 入口在设置"浏览器"页与站点信息菜单；先选 Chrome 配置文件，再勾选站点（默认不勾，没有"全部导入"），最后在主进程原生确认里说明后果；"退出即清空"模式下不可导入。
3. **解密在 Core 的 `piarc-browser-import`。** macOS：用户确认后读一次钥匙串 `Chrome Safe Storage`，PBKDF2-SHA1 派生 AES-128-CBC 密钥解密 v10，数据库版本 ≥ 24 时去掉 32 字节域哈希前缀；Windows：DPAPI 解出 `Local State` 的密钥，AES-256-GCM 解密 v10，v20（App-Bound）逐条报"不支持"。Cookies 库先复制再读（含 WAL）。密钥与明文用完清零，值在读取后登记脱敏；明文经 NAPI 交给主进程写入分区，不进渲染进程。
4. **导入站点更严。** 导入记录（工作区、站点、条数、时间、来源配置）存 Core 的 `browser_imports` 表；智能体访问这些站点时每个会话都出站点卡，没有"总是允许"，auto 与 bypass 不自动放行。设置页可逐站清除（同时删除分区中该站点的 cookie 与记录）。
5. **审计** `kind: "browserImport"` 只记站点与条数。

## 保留的风险（交付说明必须列出）

- 智能体在用户批准的导入站点上以用户身份操作；页面注入可以诱导它在这些站点上读取或提交数据。
- 钥匙串提示里若选"始终允许"，PiArc 会长期持有解密 Chrome cookie 与已保存密码的能力；导入对话框建议选"允许"。
- Windows 上分区 cookie 由 DPAPI 保护，沙箱外的命令（Windows 无 OS 沙箱，D7）以同一用户身份可以解开；与 Bash 在 Windows 上的现状同级。
- 导入的是副本，不随 Chrome 更新或登出同步。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 不支持导入 | 风险最低 | 用户明确要求 | 用户否决 |
| 全量导入 | 一步到位 | 智能体获得用户全部站点身份 | 否决 |
| cookie 存进保险箱，导航时注入 | 满足 ADR-0021 | Chromium 需要 cookie 在分区里才能工作；每次注入都等于导出明文 | 否决 |
| Windows 导入只放内存分区 | 退出即失效 | Windows 本就无沙箱，风险等级不变，导入失去意义 | 否决 |

## 后果

- 正面：用户能在内置浏览器里复用已有登录；导入范围与智能体访问都可见、可撤销。
- 负面与代价：新功能 crate 与 RustCrypto 依赖（`pbkdf2`、`cbc`、`sha1`、`hmac`）；ADR-0021 出现一类例外；Windows 现代 Chrome 的 cookie 大多无法导入。
- 需要配套做的事：`deny.toml` 检查、THR-17、`browser_imports` 迁移、设置页与 L4。

## 重新评估的触发条件

- Chrome 在 macOS 上改用应用绑定加密；
- 出现智能体在导入站点上被注入利用的报告；
- Windows 获得 OS 沙箱（ADR-0057），复核 R6。
