# Harness 参考要点

> 2026-11-14 调研快照。来源：`reference/claude-code`（社区复原的 Claude Code 工程，以仓库最早提交 `f90eee85` 作为原版对照）与 `reference/claw-code`（Rust 复刻）。本文只记录行为、数值和设计教训，不收录任何源码或提示词原文（clean-room，见 ADR-0006）。Claude Code 的公开行为以 `claude-official-capabilities.md` 为准，本文补充官方文档没有讲清的内部机制。

## 1. Claude Code 专业度的来源（按重要性排序）

### 1.1 回合不变量

- 单一主循环：助手消息中出现工具调用是继续下一轮的唯一信号。
- 流式期间就开始执行工具，不等整条消息结束。
- 连续的并发安全调用（只读类）成批并行，默认单批上限 10；其余串行。
- 中断或降级时，为所有未完成的工具调用补齐合成的结果，保证 tool_use / tool_result 配对完整。
- 可恢复错误（限流、过载）先扣住、退避重试，不立即暴露给模型。
- 自动压缩连续失败 3 次后熔断，避免空转。

### 1.2 工具契约

- 先读后改：编辑前必须读过文件；读取后文件被修改则拒绝编辑；待替换文本必须唯一。
- Read 带行号分页；文件未变化时重复读取返回存根，节省上下文。
- 单个工具结果超过 50K 字符时落盘，只给约 2KB 预览；单条消息中工具结果合计上限约 200K 字符。

### 1.3 权限

- 判定顺序：deny → ask → 工具自身检查 → 模式 → allow；bypass 模式也跨不过前几步。
- 外部发行版的 Bash 分析基于 shell 词法拆分加约 20 条正则校验与只读命令白名单。PiArc 改用 tree-sitter-bash 做语法级拆分（架构文档 6.2.2）。
- "不再询问"的规则写入项目的本地设置文件。

### 1.4 缓存友好的上下文

- system prompt 分静态段与动态段，并分段缓存（memoize）。
- 动态信息（git 状态、文件变化、任务提醒等）以 system-reminder 附件的形式随消息送达，不改写 system prompt。
- 每个请求只放一个消息级缓存断点。
- 自动压缩阈值：上下文 ≥ 窗口 − min(最大输出, 20K) − 13K。
- 压缩摘要采用固定的 9 节结构；压缩后最多恢复 5 个最近文件（合计 50K token）。

### 1.5 其他

- hooks 在原版中为 27 个事件（官方文档当前为 33 个，以官方为准）。
- 子 agent 默认完全隔离，不继承父对话。
- checkpoint 在每条用户消息时打点，改文件前备份；Bash 与子 agent 的改动不追踪。
- 各类扩展（命令、skills 等）在内部统一抽象为 Command。
- SDK 的 control 协议是双向的：宿主可以发 interrupt、切换模式、切换模型等控制请求，Claude Code 也可以向宿主发权限询问。

### 1.6 社区版的误导性改动（设计时以原版为准）

- 删除了"未读即拒绝编辑"的检查；
- plan 模式实际等同于 bypass；
- 某个扩展工具绕过了 hooks 与 ask 规则；
- WebFetch / WebSearch 默认经第三方代理。

## 2. claw-code 的经验

### 2.1 值得借鉴

1. **窄 trait 隔离 I/O 边界**（API 客户端、工具执行器、权限询问器、遥测），用内存 fake 可以确定性地测完整回合。
2. **显式的权限阶梯函数**，不依赖枚举声明顺序；未声明的工具默认要求最高权限；hook 的 allow 不能绕过 ask 与 deny。
3. **安全默认值**：项目级 hooks 默认不信任；工作区边界判断考虑符号链接与不存在的路径；凭据在调试输出中脱敏；持久化失败时回滚内存状态。
4. **配置可观测性**：报告每个配置文件的状态、命中的键、被覆盖的键，部分成功时分别列出有效与无效项。
5. **调用对账**：请求状态 Accepted → Running → Terminal，进程重启后未完成的标为 Uncertain，配合幂等键。
6. **"如实报告不支持"**：以结构化状态告诉集成方某能力不可用。
7. **对外 JSON 输出受契约测试保护**，错误带类型化的 kind。

### 2.2 必须规避

1. 上帝文件与上帝 crate（单文件 2 万行、单 crate 约 50 个模块）。
2. 定义了却没接线的模块（例如一千多行的 Bash 校验从未被调用）——代码量不等于能力。
3. 同一功能多套实现（两个 hook 执行器、三套压缩机制）。
4. 同步批量的回合模型，渲染与执行耦合。
5. 工具语义偏离：多处匹配时静默替换第一处、伪 diff、后台命令丢弃输出、超时不杀进程、子 agent 不返回结果。
6. 进程管理隐患：管道不读取导致缓冲死锁、只杀直接子进程。
7. 协议互通问题：MCP stdio 用了错误的分帧，测试 mock 犯同样的错误，因此测试照样通过。
8. 字符串化的错误流，靠字符串包含关系分类错误。
9. 文档与代码漂移：两份能力清单互相矛盾、长期不更新；测试名与断言不符；找不到 fixture 就静默通过。

### 2.3 parity 测试方法（PiArc 采纳并改进）

- 采纳：mock provider 按场景标记返回脚本化流式响应；在干净环境中运行真实二进制；同时断言输出、文件副作用与 mock 收到的请求序列；场景清单与能力清单双向映射。
- 改进（架构文档第 12 章）：mock 必须校验请求合法性；场景写成数据文件，每个场景一个独立测试；增加对真实 Claude Code 的录制与结构化比对；能力清单使用稳定 ID，状态由测试结果自动生成。
