## 执行要求

开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

R5 是 M4 → M5 的阶段门。M4 的退出标准有两条（第 16 章）：安全威胁表逐条有测试；性能预算全部达标。本任务逐条取证，组织四个独立的只读审查（安全、性能、无障碍、工程质量），核实每条发现并处理，确认 W3 的 Windows M3 结论，最后给出"M4（macOS）是否达标、能否进入 M5"的结论。

评审本身不做新功能。确认的问题直接修复（先写失败测试）；规模超出评审的登记到 PLAN。

## 范围

### 要做

- M4 两条退出标准逐条取证；M4 目标逐项核对。
- 四个独立只读审查（并行），逐条核实并处理。
- 写 `docs/reviews/R5-findings.md`，更新 `docs/reviews/README.md`。
- 确认 W3 结论；核对 T39 Windows 隔离 ADR 的状态。
- 更新架构第 16 章状态与第 6.0 节能力矩阵；给出结论与 W4 的 M4 验收清单。

### 不做

- M5 的任何功能（T46 起）。
- 放宽性能预算或安全基线：达不到的项按第 14 章与决策分级处理，不在评审中改标准。

## 交付物

### 1. 退出标准取证

- **安全**：运行 T45 的威胁检查，确认两个平台 CI 上映射引用的测试全部通过；每条威胁抽查至少一个测试，读断言确认它真的在验证对策（不是只验证功能可用）。抽查记录写进发现文件。
- **性能**：核对 T44 的 macOS 实测数据全部达到第 11 章预算，最近一次 Nightly 完整测量通过；W3 的 Windows 数据逐项列出，未达标项按第 15.1 节归入 W4，不阻断 M4（macOS）结论。
- **M4 目标**：第 16 章 M4 行的每一项（macOS 沙箱、Windows 隔离评估、插件、NotebookEdit、可操作通知、配置诊断、无障碍、本地化、性能进 CI）对应到任务与验收证据；T39–T45、W3 的验收项全部为 `passing`，或为 `blocked` 且原因成立；`capabilities.md` 无 MISSING，`--milestone M4` 不列出 `planned` 能力。

### 2. 独立审查

- 用子代理并行开四个只读审查，每个只给范围与材料，不给你自己的判断，避免先入为主：

| 维度 | 范围 | 重点 |
|---|---|---|
| 安全 | piarc-sandbox、piarc-policy、插件管理、piarc-telemetry、主进程 IPC 与 preload，以及 R4 之后的相关提交 | 威胁模型对策的绕过路径、沙箱与 Agent Host 配置、插件信任与再确认、脱敏遗漏、XSS 渲染面 |
| 性能 | 测量框架、门禁配置、基线、长跑测试，以及事件转发与渲染热路径 | 测量口径是否与第 11 章一致、门禁能否真的拦住回归、噪声与误报、热路径上的明显浪费 |
| 无障碍 | 渲染进程组件、a11y 状态清单、i18n 资源与检查脚本 | 状态清单漏项、可访问名称、焦点管理、播报节流、硬编码字符串 |
| 工程质量 | M4 期间的全部改动 | 编码规范、文件与函数长度、错误类型化、测试纪律（无 skip、无放宽）、CLAUDE.md 与代码一致、`TODO(Txx)` 残留 |

- 每个审查的输出格式与 `docs/reviews/README.md` 一致：编号、维度、文件与行号、失败场景、建议。审查只读，不修改文件。

### 3. 核实与处理

- 每条发现亲自核实：能复现的写失败测试，再修复并提交；不同意的写理由；规模超出评审的登记到 PLAN 并写编号。
- `docs/reviews/R5-findings.md`：审查说明（每个审查的范围与输入）、退出标准取证、全部发现与处理、结论。`docs/reviews/README.md` 中 R5 一行填写结论。

### 4. W3 与 T39 ADR

- W3：核对 `PLAN.md` 中的 W3 结论与证据，确认 Windows 的 M3 退出标准逐条达标、遗留问题有归属。
- T39 的 Windows 隔离 ADR：已接受时核对架构第 6.10、15.2 节与第 14 章 R16 已同步；仍为"提议"时，在结论中列为进入 M5 之前需要用户决定的事项。

### 5. 结论

- M4（macOS）是否达标；进入 M5（T46）的前提条件。
- W4 需要在 Windows 上验收的 M4 项清单，写在发现文件末尾。
- 按第 18 章更新架构第 16 章状态与第 6.0 节能力矩阵，递增版本号并写修订记录。

## 实现要点

- 审查子代理要相互独立：同时启动，各自只拿本维度的范围与材料。收到结果后由你核实，不要把子代理的结论直接当作事实。
- 修复评审发现时遵守原任务的范围与决策分级：属于变更型的写 ADR 提议，不在评审中直接改基线。
- 取证引用具体的命令输出、文件路径与提交，不写"已验证"这类没有出处的结论。
