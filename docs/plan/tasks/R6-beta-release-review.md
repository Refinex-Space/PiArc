开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

R6 是最后一个阶段门：判断 PiArc 能否在 macOS 与 Windows 上同时公开 Beta（架构第 16 章 M5 退出标准）。T51 证明了九个核心场景能跑通，R6 从更宽的角度复核：

- 从 M0 到 M5，每个里程碑的退出标准在两个平台上是否都有证据；
- 第 14 章的每条风险、每份 ADR 的重新评估触发条件，现在处于什么状态；
- 还有哪些技术债和未通过的验收项，它们是否阻塞 Beta；
- 几位独立审查者在不受实现者思路影响的情况下，能发现什么问题。

结论只有两种：可以公开 Beta（附前提条件），或者不可以（附必须先解决的问题）。发布动作由用户执行。

## 范围

### 要做

- M0–M5 汇总、风险复核、ADR 触发条件复核、技术债排序。
- 独立只读审查（并行），逐条核实后处理。
- 合规复核；把设计增补并入架构正文；更新架构第 16 章与能力矩阵。
- "公开 Beta"结论。

### 不做

- 公开发布、对外宣布、申请 SignPath 签名等需要用户身份的操作。
- 修复审查中确认的、不阻塞 Beta 的问题：登记即可，留给 Beta 后的任务。

### 2. 独立只读审查

至少五个审查同时进行，用只读审查子代理，每个只给审查范围与代码位置，不给你的判断：

| 审查 | 范围 |
|---|---|
| 安全与隐私 | Electron 加固与 IPC、权限与 Auto 模式、托管配置、凭据保险箱、诊断包脱敏 |
| 更新与发布链 | 发布流水线、签名环境、清单校验、两个平台的更新路径、`THIRD_PARTY_NOTICES` |
| 数据完整性与可靠性 | 检查点与回退、会话存储与索引重建、Agent Host 崩溃恢复、更新后数据保留 |
| Harness 行为 | 工具不变量、hooks、子 agent 与 fork、压缩与缓存、自动记忆 |
| 工程质量与文档一致性 | 代码与架构、ADR、CLAUDE.md 是否一致；测试纪律（第 12.6 节） |

每条发现亲自核实：确认且阻塞 Beta 的修复（先写复现测试），确认但不阻塞的登记；不同意的写明理由。

### 3. 合规复核

- Anthropic 订阅 OAuth 仍被屏蔽（CI 测试通过）。
- 全部自写提示词（system prompt、压缩摘要、WebFetch 提取、Auto 模式审查、输出风格等）的原创性自查记录齐全。
- 产品名、图标、界面中没有 Anthropic 品牌资产；`THIRD_PARTY_NOTICES` 完整；fork 与复用的 MIT/Apache 代码保留了版权声明并注明来源。

### 4. 架构文档更新

- 把 `docs/architecture/addenda/` 中已实现的设计增补（T46、T47 等）并入正文对应章节。
- 更新第 16 章 M0–M5 状态、第 6.0 节能力矩阵；递增架构版本号并写修订记录。

### 5. 结论

- "可以公开 Beta"或"不可以"，二选一。可以时列出前提条件（例如用最终提交重新运行一次 T50 的发布流水线生成草稿发布）；不可以时列出必须先解决的问题与建议的任务。
- 列出需要用户做的事：公开草稿发布；以及随 Beta 到来的决定，例如 ADR-0018 中"首个公开版本后申请 SignPath 免费签名"、WinGet 评估，需求 D4、D6 的后续评估。
- 更新 `docs/reviews/README.md` 中 R6 的结论一列。

## 实现要点

- 汇总引用证据，不重新描述：每个结论后面跟证据位置（文件、提交、测试输出）。
- 审查子代理只读；修复由你在核实后进行。
- 风险与触发条件复核要写"当前事实"，例如实际的补丁数、Pi 最近两次升级耗费的人日、Electron 版本是否仍在支持期内。

## 验收标准

- [R6-A01] `R6-findings.md` 的里程碑汇总覆盖 M0–M5，每个退出标准在两个平台上都有证据链接或明确写明缺失。验证：文件内容。
- [R6-A02] `acceptance.json` 中所有状态不是 `passing` 的项都被列出，并写明原因、是否阻塞 Beta、后续去向。验证：用脚本列出非 `passing` 项并与文件比对。
- [R6-A03] 第 14 章 R1–R18 逐条有当前状态、证据、是否触发与处理。验证：文件中的风险表。
- [R6-A04] 每份"已接受"的 ADR 的重新评估触发条件逐条检查，已触发的有 ADR 提议或记录的决定。验证：文件中按 ADR 编号的检查表。
- [R6-A05] 技术债清单按写明的排序标准排列，每条有来源与建议的处理时间点。验证：文件内容。
- [R6-A06] 至少五个独立只读审查并行完成，每条发现都有处理：已修复（提交）、不同意（理由）或已登记（编号）。验证：审查发现表。
- [R6-A07] 阻塞 Beta 的确认问题全部修复，每个修复有先失败后通过的回归测试。验证：测试输出与提交。
- [R6-A08] 合规复核三项全部有结论：订阅 OAuth 屏蔽测试通过、提示词原创性自查记录齐全、品牌资产与第三方许可证检查通过。验证：测试输出与检查记录。
- [R6-A09] 已实现的设计增补已并入架构正文，第 16 章与第 6.0 节已更新，架构版本号已递增并有修订记录。验证：文档改动。
- [R6-A10] 结论明确为"可以公开 Beta"或"不可以"，附前提条件或必须先解决的问题，并列出需要用户执行的事项；`docs/reviews/README.md` 已更新。验证：文件内容。
- [R6-A11] `npm run verify` 通过。验证：命令输出。
