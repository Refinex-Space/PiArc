## 背景与目标

Auto 模式用一个可配置的审查模型代替人逐项审批：规则和模式默认能决定的调用照常处理，原本要弹审批卡的调用交给审查模型判定。它是架构第 6.2.1 节中唯一留到 M5 的模式，也是权限系统里风险最高的一处：审查模型判错，等于替用户点了"允许"。

所以本任务分两段。第一段只写设计增补，讲清审查模型看到什么、输出什么、失败时怎么办、和既有规则怎么排序，交给用户确认。第二段按确认后的设计实现，用 L2 场景和 mock provider 的请求断言覆盖每条判定路径。

完成后，用户可以在用户级设置中开启 Auto 模式；每次审查都有审计记录；审查失败一律退回人工审批；仓库里的配置无法开启它。

## 交付物

### 设计增补（关口前）

### 1. `docs/architecture/addenda/T46-auto-mode.md`

每节给出结论与理由；有多种做法时列出备选并给推荐。

| 节 | 必须回答的问题 |
|---|---|
| 输入与输出 | 审查模型看到哪些内容（用户消息、当前工具调用、近期工具调用摘要、工作区与可信基础设施）；工具结果、网页、MCP 返回等不可信内容是否进入、如何隔离以抵抗提示注入；是否接受 PostToolUse hook 提供的 `classifierContext`；输出的结构化格式（允许 / 拒绝 / 不确定 + 理由），用结构化输出还是单一工具调用 |
| 审查策略 | 默认拦截类别（用自己的话写，例如下载即执行、外发敏感数据、不可逆删除、改写他人提交、生产部署）；用户如何补充可信基础设施与自定义策略；可选审查模型的能力门槛（第 6.13 节能力表中的哪些字段） |
| 失败处理 | 超时、服务商错误、限流、输出无法解析、结论不在枚举内时的行为（一律转人工审批）；超时默认值；连续拒绝达到多少次后回退为人工审批并提示 |
| 审计 | `audit_events` 中记录的字段（会话、子 agent、工具调用、审查模型、结论、理由、耗时、token、输入摘要的哈希）；保留策略 |
| 成本 | 每次审查的 token 与成本如何计入 T41 的用量统计；审查请求的缓存布局（稳定的 system 段在前） |
| 与规则、模式的关系 | 审查步骤在第 6.2.3 节流水线中的位置（相对 PermissionRequest hooks）；deny、ask 规则先于审查；哪些调用始终询问、不交给审查模型（关键路径删除、`AskUserQuestion`、`requiresUserInteraction` 类工具、受保护路径写入是否属于此类）；子 agent 与后台任务是否适用 |
| 启用与作用域 | 只能在用户级设置开启并二次确认；项目级 `.piarc/settings*.json`、`.claude/settings*.json` 不能开启 Auto 模式，也不能设置审查模型、审查策略与可信基础设施（防止仓库把审查指向宽松的端点） |

增补末尾单列"需要用户确认的要点"，至少包括：不可信内容是否进入审查输入、默认拦截类别、始终询问的类别、连续拒绝阈值、审查模型能力门槛、子 agent 是否适用。

### 实现（关口后）

### 2. 判定步骤（piarc-policy）

- 在增补规定的位置加入 auto 步骤；deny、ask 规则与"始终询问"类别先于它生效。
- 审查进行中，审批账本把该请求标为"审查中"；结论回来后按允许、拒绝（理由回给模型）、不确定（转人工审批卡）处理。
- 失败路径统一归一为"转人工审批"，不执行工具调用；连续拒绝计数与回退按增补实现。

### 3. 审查调用（Harness Kit）

- 沿用 T29 的辅助模型调用通道，方法名与调用方向以 T29 的实现为准。审查请求独立于主会话，不写入主会话历史。
- 审查提示词放在单一文件中，原创编写；结构化结果在 Core 侧再校验一次。

### 4. 设置、审计与成本

- 用户级设置：启用开关（二次确认）、审查模型（只列出满足能力门槛的模型）、自定义策略与可信基础设施。
- 项目级出现这些键时忽略，并在配置诊断中标为"已忽略"及原因。
- 审计写入与审计页筛选；用量统计中单列"审查"一类。

### 5. 客户端

- 环境栏模式菜单增加"自动审查"，未在设置中开启时不可选并给出说明；切换写入转录。
- transcript 中由审查模型放行或拒绝的工具调用带标识，可展开查看理由；审查模型不可用时环境栏显示状态。

### 6. L2 场景与能力 ID

- `tests/scenarios/perm-auto-*.yaml` 覆盖每条判定与失败路径，能力 ID 例如 `CAP-PERM-AUTO-ALLOW-001`。
- mock provider 为主模型与审查模型分别编排响应；请求断言覆盖审查请求的必含段落与排除内容。

## 实现要点

- Agent Host 在等待 `policy/evaluate` 时会收到 Core 发来的审查请求。确认 Agent Host 能并发处理入站请求，避免互相等待；写一个并发工具调用的场景专门覆盖。
- 结论只接受枚举值；理由字段截断后再写入审计和 UI，避免超长文本。
- 测试全部用 mock provider，不调用真实模型。需要用真实模型观察审查质量时，先说明预计调用次数并征得用户同意。

## 验收标准

- [T46-A01] 设计增补 `docs/architecture/addenda/T46-auto-mode.md` 覆盖输入与输出、审查策略、失败处理、审计、成本、与规则和模式的关系、启用与作用域七节，并列出需要确认的要点；用户已确认。验证：增补文件与用户确认记录。
- [T46-A02] Auto 模式下，审查模型返回允许、拒绝、不确定时，分别执行工具调用、拒绝并把理由回给模型、转为人工审批卡。验证：L2 场景与 mock provider 请求断言。
- [T46-A03] 审查超时、服务商返回错误、输出无法解析、结论不在枚举内四种情况都转为人工审批，工具调用不执行。验证：L2 场景（故障注入）。
- [T46-A04] 命中 deny 规则时直接拒绝、命中 ask 规则时转人工审批，两种情况下 mock provider 都没有收到审查请求；增补列为"始终询问"的类别同样不发审查请求。验证：L2 场景与请求记录断言。
- [T46-A05] 项目级 `.piarc/settings*.json` 与 `.claude/settings*.json` 不能开启 Auto 模式，也不能设置审查模型、审查策略与可信基础设施；这些键在配置诊断中标为"已忽略"。验证：测试与配置诊断输出。
- [T46-A06] 审查请求的结构符合增补的输入规格：必含段落与排除内容各至少一条断言通过。验证：mock provider 请求断言。
- [T46-A07] 连续拒绝达到增补规定的阈值后回退为人工审批，并在界面提示。验证：L2 场景与 Playwright。
- [T46-A08] 每次审查写入审计表，字段与增补一致；设置中的审计页可筛选"审查模型决定"。验证：测试与 Playwright。
- [T46-A09] 审查调用的 token 与成本计入用量统计，并单列为"审查"一类。验证：测试（价格表注入）与 Playwright 截图。
- [T46-A10] 子 agent 的工具调用按增补规定处理；适用时审计记录标明来源子 agent。验证：L2 场景。
- [T46-A11] 模式菜单在未开启时不可选并说明原因；开启后可选"自动审查"；transcript 中放行与拒绝的调用带标识和可展开的理由；审查模型不可用时环境栏显示状态。验证：Playwright 与截图（`tmp/evidence/T46/`，亮/暗）。
- [T46-A12] 审查提示词位于单一文件且为原创，报告附逐段的原创性自查记录。验证：文件与自查记录。
- [T46-A13] `npm run verify` 通过（含 Windows CI 上的 L2 场景）。验证：命令输出。
