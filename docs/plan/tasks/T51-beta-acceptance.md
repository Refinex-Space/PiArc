## 执行要求

开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

之前的任务按能力逐项验收，本任务按用户的完整工作流验收：需求第 3 章的九个核心场景 S1–S9，在两个平台上用打包后的发布候选构建从头到尾跑一遍。它回答的问题是"一个开发者装上 PiArc 之后，这九件事能不能顺利做完"。

验收用同一个提交的发布候选构建（T50 流水线或本地打包），不用开发模式。每个场景一个 Playwright 端到端用例，配合必要的手工步骤（系统通知、浏览器授权、首次运行放行）。同时确认三项发布门槛：能力清单无 MISSING、第 11 章性能预算两个平台达标、安全清单通过。不能在 Beta 前修复的问题进入已知问题列表。

完成后，R6 拿到一份按"场景 × 平台"整理的证据矩阵和一份已知问题列表。

## 范围

### 要做

- S1–S9 的端到端用例与手工步骤，两个平台各执行一次并留证据。
- 能力覆盖、性能预算、安全清单三项门槛的复核（发布候选提交）。
- 修复阻塞 Beta 的缺陷；整理已知问题列表；验收报告。

### 不做

- 新功能，以及非阻塞问题的修复（进入已知问题列表）。
- 公开发布（R6 给结论后由用户执行）。

## 交付物

### 1. 端到端用例

- `apps/desktop/tests/e2e/beta/` 下每个场景一个用例文件，驱动打包后的应用，模型侧用 mock provider。两个平台共用同一套用例，只在主进程平台模块覆盖的地方分支。

| 场景 | 用例必须覆盖 |
|---|---|
| S1 修复失败的测试 | 读、改、跑测试；按权限模式审批；Changes 面板逐文件审阅 |
| S2 先规划 | 计划模式只读探索、行内评论、批准时选择模式、执行中的任务清单 |
| S3 三件事并行 | 三个会话各在独立 worktree 并行；侧栏状态；窗口不在前台时的审批通知；期间主进程事件循环延迟在预算内 |
| S4 回退 | 选择用户消息，回退代码、对话、两者；外部修改导致的冲突提示 |
| S5 探索陌生代码库 | 只读探索子 agent 使用别名指定的便宜模型，并行搜索后汇总 |
| S6 接入团队工具 | stdio 与 HTTP + OAuth（mock 授权服务器）两种 MCP server，工作区内会话共享连接 |
| S7 迁移 Claude Code 配置 | 带 `.claude/` 的仓库中 memory、权限规则、hooks、agents、skills、commands 生效，配置诊断列出生效与忽略项 |
| S8 长任务 | 后台运行开发服务器，agent 继续工作，任务完成后通知注入 |
| S9 切换模型 | 会话中途从 Anthropic 线格式切到 OpenAI 兼容线格式，显示切换代价，会话继续 |

### 2. 手工步骤

- 每个场景中自动化覆盖不到的步骤（系统通知与角标、浏览器授权页、读屏抽查）写成清单，两个平台各执行一次，结果记入验收报告。
- 首次运行：macOS（15 与 26，有条件时）与 Windows 11 的干净环境中，按 README 安装并打开，由用户操作，智能体准备产物与清单。

### 3. 发布门槛复核

- 两个平台 CI 生成的 `capabilities.md` 无 MISSING，且 `check-capabilities.mjs --milestone M5` 不再列出 `planned` 能力。因上游阻塞而无法实现的能力（例如 T48 登记的 MCP elicitation）保持在清单中，状态为 `blocked` 并带原因与链接（T15 定义的状态），由 R6 判断是否影响 Beta；不得删除或改名。
- T44 的完整性能测量在两个平台的基准机上用发布候选提交运行。
- 发布候选产物：fuse 检查、清单签名与哈希、Electron 官方安全清单复核、威胁表测试、依赖审计（无未处理高危）。

### 4. 缺陷与已知问题

- 阻塞 Beta 的缺陷：场景无法完成、数据丢失、安全问题、崩溃。先写复现测试再修复。
- `docs/beta/known-issues.md`：每条写明平台、严重度、影响、规避方法、跟踪位置（登记事项编号）；发布说明模板链接到它。

### 5. 验收报告

- `docs/beta/T51-acceptance-report.md`："场景 × 平台"矩阵，每格写结果与证据位置（Playwright 报告、截图 `tmp/evidence/T51/<平台>/`、手工记录），以及三项门槛的数据。

## 实现要点

- 两个平台必须用同一个提交。macOS 部分结束时记下提交哈希，Windows 部分开工时核对；中途修了缺陷，就在两个平台重跑受影响的场景。
- 用户同意时，S1 与 S9 各用一家真实服务商在两个平台补跑一次，作为补充证据；先说明预计调用次数，只用最便宜够用的模型。
- 场景用例名与断言内容一致（第 12.6 节），不写"找不到就跳过"的分支。

## 验收标准

- [T51-A01] S1–S9 各有一个驱动打包应用的端到端用例，在 macOS 上全部通过。验证：Playwright 报告与截图（`tmp/evidence/T51/macos/`）。
- [T51-A02] 同一套用例在 Windows 上全部通过。验证：Playwright 报告与截图（`tmp/evidence/T51/windows/`）。
- [T51-A03] 每个场景的手工步骤在两个平台各执行一次，结果记入验收报告。验证：报告中的记录（日期、平台、结果）。
- [T51-A04] 两个平台的干净环境中，用户按 README 完成首次安装与打开，结果记入验收报告。验证：用户实机操作记录。
- [T51-A05] 两个平台 CI 生成的 `capabilities.md` 中没有 MISSING，`--milestone M5` 不列出任何 `planned` 能力；`blocked` 能力逐条列在已知问题列表中并注明登记事项编号。验证：生成命令与检查命令的输出。
- [T51-A06] 发布候选提交在 macOS 基准机上满足第 11 章全部预算。验证：测量输出。
- [T51-A07] 发布候选提交在 Windows 基准机上满足第 11 章全部预算。验证：测量输出。
- [T51-A08] 发布候选产物的 fuse 检查、清单签名与哈希校验、Electron 安全清单复核、威胁表测试全部通过，依赖审计无未处理高危。验证：各脚本与测试输出。
- [T51-A09] 阻塞 Beta 的缺陷全部修复，每个修复有先失败后通过的回归测试。验证：缺陷清单、提交与测试输出。
- [T51-A10] `docs/beta/known-issues.md` 中每条问题都有平台、严重度、影响、规避方法、跟踪位置，发布说明模板已链接。验证：文件内容。
- [T51-A11] `docs/beta/T51-acceptance-report.md` 的"场景 × 平台"矩阵每格都有结果与证据位置，两个平台使用同一个提交。验证：文件内容与提交哈希。
- [T51-A12] macOS 与 Windows 上 `npm run verify` 都通过。验证：两个平台的命令输出。
