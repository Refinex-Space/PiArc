## 执行要求

开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

R1 是 M0 的阶段门，结论决定能否开始 M1：看板中 T13 的依赖是"R1 结论为进入 M1"。M0 用代码验证了十个高风险假设，R1 回答三件事：

1. 每个验证项在两个平台上的结论是什么，有没有触发 ADR 的重新评估条件；
2. M0 的代码是正式实现的起点，质量是否过关：用四个独立的只读审查找问题，逐条核实后处理；
3. 第 11 章的性能预算按实测校准，作为 M1 起的基线。

最后给出明确结论：进入 M1、有条件进入（列出前提），或不进入（列出必须先处理的项）。

5. `docs/reviews/README.md`（发现记录格式）；`docs/engineering/` 下三份工程规范。

## 范围

### 要做

- M0 总结 `docs/spikes/M0-summary.md`。
- ADR 触发条件逐条检查。
- 四个独立只读审查；逐条核实并处理，记录在 `docs/reviews/R1-findings.md`。

## 交付物

### 1. M0 总结

`docs/spikes/M0-summary.md`：

- 总表：S1–S10 × macOS、Windows 两列，结论（通过 / 有条件通过 / 不通过 / 未验证）、关键数据、报告链接。S3、S4、S9、S10 的 Windows 结论以 CI 运行结果为依据。
- 有条件通过与未验证项：条件、风险、跟进任务。
- 对后续任务有影响的结论（例如 S7 的路线、S1 选定的库、S8 的受保护路径清单、Job Object 的放置），列出受影响的任务编号。

### 2. ADR 触发条件检查表

- 逐条列出 ADR-0013–0018 的重新评估触发条件，以及 ADR-0004、0009、0010 中与 S4、S9、S3 相关的条件：条件原文、M0 证据、是否触发。
- ADR-0015 与 ADR-0018 中留给 M0 的事项逐项给出结论：hardened runtime、系统通知、钥匙串弹窗次数、`LoadBrowserProcessSpecificV8Snapshot` fuse、Velopack 接入、TCC 责任归属、npx 原生模块加载。没有结论的项列为前提条件，或指派到具体任务。
- 已触发的条件：按 `docs/adr/README.md` 的规则写新 ADR（状态"提议"），在结论中列为阻塞项。

### 3. 独立审查

用四个只读子代理并行审查。每个子代理只拿到维度、范围和必读材料，不给你的判断，避免结论被锚定：

| 维度 | 范围 | 重点 |
|---|---|---|
| Electron 安全与 IPC | `apps/desktop/`、Forge 配置、fuses、CSP | 第 10.3 节与 S10 清单的落实；IPC 来源校验；preload 暴露面；导航与外链；Markdown 渲染路径；权限放行清单 |
| Core/NAPI 并发与错误边界 | `crates/` 中 core、napi、term、secrets、sandbox、exec、fs | panic 边界；`ThreadsafeFunction` 生命周期与关闭顺序；取消传播；阻塞主进程事件循环的调用；`unsafe` 与 `SAFETY` 注释；错误类型化；凭据不落盘 |
| Agent Host/AHP 健壮性 | `agent-host/`、`piarc-host`、`piarc-protocol`、`packages/protocol` | 握手与版本；背压与内存上界；重启与 `uncertain` 对账；失败即拒绝；超时；帧边界；多会话串扰；凭据适配层 |
| 工程质量与 CLAUDE.md 一致性 | 整个仓库 | 工程规范符合度；文件与函数长度；测试纪律（没有 skip 与静默通过）；依赖锁定与许可证；文档与实现漂移；CLAUDE.md 中的命令与结构是否属实、长度是否超限；`TODO` 清零 |

- 每个子代理返回发现：文件与行号、失败场景、严重程度、依据。
- 由你逐条核实：能复现，或能指出具体代码路径的，才算确认。确认的问题先写失败测试再修复，每个修复单独提交；不同意的写理由；范围大的登记到 `PLAN.md`"登记事项"或"技术债"。
- `docs/reviews/R1-findings.md` 按 `docs/reviews/README.md` 的格式记录每条发现；更新该 README 中 R1 的结论列。

### 4. 预算校准

- 第 11 章每一行列出：两个平台的 M0 实测值（没有测量的写"未测"）、原预算、校准后预算。
- 只收紧：实测明显优于预算的行，收紧到实测值加余量，余量规则写进修订记录；实测超出预算的行不放宽，作为问题处理（指派优化任务，或按 ADR 触发条件处理）；确需放宽的，在第 18 章修订记录中写明原因。
- 同步架构文档中与 M0 结论不一致的地方，例如第 16 章 spike 状态、第 8.4 节的库与参数、第 6.10 节的沙箱受保护路径、第 10.3 节的 hardened runtime；递增架构版本号并写修订记录。

### 5. 结论

- M0 登记事项逐条归属：指派到具体任务，或关闭并写理由。
- 结论写入 `M0-summary.md`、`docs/reviews/README.md` 与 `PLAN.md` 会话日志：进入 M1 / 有条件进入（前提条件清单，每条有负责任务和检查时间点）/ 不进入（必须先处理的项）。

## 实现要点

- 子代理只用于相互独立的审查；核实、修复、写文档由你自己完成，不用子代理复查自己的工作。
- 修复同样要满足质量门禁；修复涉及变更型决策时，写 ADR 提议，不在评审中直接改变架构。
- 结论要能执行：每个"有条件"都写清条件是什么、谁负责、什么时候检查。
