## 执行要求

开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

T13–T22 交付了 M1 可行走骨架：存储与信任、会话编排与投影、L2 场景基座、文件工具与 Bash、客户端外壳、transcript 与 composer、基础审批、模型与凭据、system prompt 与 memory。R2 是 M1 的阶段门，结论决定能否进入 M2。

第 16 章的 M1 退出标准有两条：能用至少 2 家服务商完成"读代码 → 改代码 → 跑测试"的完整任务；L2 场景 ≥ 20 个通过。本任务逐条取证，并用四个相互独立的只读审查找出实现中的问题，逐条核实与处理，最后给出 M1（macOS）是否达标的结论和 W1 的检查清单。

## 必读

1. 架构设计：第 16 章（M1 目标与退出标准）、第 6.0 节能力矩阵中里程碑含 M1 的行、第 6.1.4 节中 M1 的工具、第 10.1 节威胁模型、第 15.2 节、第 18 章（里程碑结束时的文档更新）。
2. `docs/plan/acceptance.json` 中 T13–T22 的验收项；`PLAN.md` 中 M1 的会话日志与登记事项。
3. `docs/reviews/R1-findings.md`（上次评审遗留项）、`docs/reviews/README.md`（发现记录格式）。
4. `tests/capabilities.yaml`、`docs/product/capabilities.md`；T15 的 L2 运行命令；T21 的服务商配置方式。
5. `docs/plan/tasks/W1-windows-m1-parity.md`（W1 将按本任务的清单执行）。

## 范围

### 要做

- 按 M1 退出标准取证：两家服务商的完整任务、L2 场景数。
- 核对第 16 章 M1 目标中的每一项都已交付；T13–T22 验收项状态。
- 四个独立只读审查，逐条核实发现并处理。
- 写 `docs/reviews/R2-findings.md`：证据、发现、W1 检查清单、结论。
- 更新架构第 16 章 M1 状态与第 6.0 节矩阵。

### 不做

- M2 功能（T23 起）。审查中发现的、属于后续任务范围的缺口登记给对应任务，不在本任务实现。
- Windows 上的 M1 验收（W1）。本任务只产出 W1 的检查清单。

## 交付物

### 1. 完整任务

- 夹具仓库：一个小型项目，含一个失败的单元测试（路径含空格与中文）。任务：让 agent 读代码定位原因、修改代码、运行测试直到通过。
- 两家服务商：经设置页配置两种线格式的服务商（Anthropic Messages 形态与 OpenAI 兼容端点），在应用界面中各完成一次完整任务，用 Playwright 驱动并截图；审批在手动模式下经审批卡完成，至少一次 Bash 运行测试、一次 Edit 修改文件。
- 真实服务商：先向用户说明预计调用次数、所用模型与费用估计，征得同意后用最便宜够用的模型在同一夹具上跑一次（本机有本地模型时可以用它，无费用）。用户不同意或没有提供密钥时，在评审文件中写明"真实服务商未验证"，并在结论中作为前提条件或风险列出。
- 记录服务商组合与任务步骤，供 W1 原样复用。

### 2. 场景与覆盖

- 运行全部 L2 场景，记录通过数（必须 ≥ 20）。
- 映射表：第 16 章 M1 目标中的每一项（单工作区、多会话列表、流式对话、六个工具经 Core、PowerShell（Windows）、两种模式的基础审批、模型与凭据设置、会话持久化与恢复、transcript P0 行类型）→ 能力 ID 或 L4 用例 → 证据。没有证据的项即为缺口：属于 M1 的在本任务补测试或修复。
- 重新生成 `docs/product/capabilities.md`，确认没有 MISSING；运行 `node scripts/plan/check-capabilities.mjs --milestone M1`，确认里程碑不晚于 M1 的能力没有仍为 `planned` 的（`blocked` 的逐条说明）。

### 3. 独立审查

并行启动四个相互独立的只读审查子代理（只有读取与搜索工具，不能改文件）。每个审查者拿到审查范围、相关文件、架构章节与威胁模型，不给出你的预判：

| 审查 | 范围 |
|---|---|
| 权限与审批安全 | piarc-policy、审批账本、`policy/evaluate` 的失败路径、项目信任闸门、`trust/get`、"总是允许"的写入与原生确认、热键与防误触、模式解析（项目级 bypass/auto） |
| 工具不变量与数据安全 | piarc-fs、piarc-diff、piarc-exec、piarc-store、piarc-secrets；先读后改、保真写入、原子写、路径边界与受保护路径、截断落盘、进程树终止、命令环境、JSONL 只读、凭据只在保险箱 |
| 渲染进程安全与 IPC | preload 白名单、主进程 origin 校验、Markdown 与工具输出的渲染路径、XSS 载荷集覆盖、外部链接与导航、附件与删除会话等有副作用的命令 |
| 工程质量 | crate 依赖规则、错误类型化、函数与文件长度、测试纪律（场景名与断言一致、无静默通过）、能力清单双向映射、CLAUDE.md 与代码一致、通用能力复用表 |

### 4. 发现处理

- 每条发现逐条核实：能复现的先写失败测试再修复；不同意的写理由；属于后续任务的登记到 `PLAN.md`"登记事项"并指定任务。
- `docs/reviews/R2-findings.md` 按 `docs/reviews/README.md` 的格式记录每条发现：编号、维度、文件与行号、失败场景、核实结论、处理。

### 5. W1 检查清单

写在评审文件中，W1 逐条执行：

- 第 16 章 M1 退出标准：同一服务商组合的完整任务、L2 ≥ 20。
- 第 15.2 节中 M1 的平台差异：Git Bash 与 PowerShell、Job Object 进程树、路径（盘符、UNC、长路径、保留文件名）与 CRLF、数据目录、凭据管理器。
- 只有实机能确认的行为：中文输入法、系统通知与任务栏覆盖图标、Mica 外观。
- `acceptance.json` 中 T13–T22 因"需要 Windows 实机"而为 `blocked` 的验收项，逐条列出编号。
- 本次审查中与平台相关的发现。

### 6. 文档与结论

- 架构第 16 章标注 M1（macOS）状态，第 6.0 节矩阵中 M1 行与实现一致；递增版本号并写修订记录。
- 结论写在评审文件开头：M1（macOS）是否达标、进入 M2 的前提条件（例如真实服务商未验证、未修复的高严重度发现）、W1 的重点。

## 实现要点

- 审查子代理之间互不可见，避免结论趋同；你只在汇总时合并重复项。审查者的原始输出保留在评审文件附录中。
- 修复审查发现时遵守原任务的范围与验收项，不顺手重构；修复后跑受影响 crate 或包的测试，收尾时跑一次全量 verify。
- 发现若需要改变架构或 ADR 的既定内容，按变更型决策写 ADR 提议，并在结论中列为前提条件。

## 验收标准

- [R2-A01] 两种线格式的服务商在应用界面中各完成一次"读代码 → 改代码 → 跑测试"，夹具测试由失败变为通过，过程中至少一次 Bash 与一次 Edit 经审批卡批准。验证：Playwright 流程、测试输出与截图（`tmp/evidence/R2/`）。
- [R2-A02] 真实服务商的完整任务在用户同意后执行并记录调用次数与费用；未执行时评审文件写明原因，结论中列为前提条件或风险。验证：评审文件内容与会话记录。
- [R2-A03] L2 场景通过数不少于 20，`docs/product/capabilities.md` 重新生成且没有 MISSING，`--milestone M1` 不列出 `planned` 能力。验证：L2 运行输出与两条命令的输出。
- [R2-A04] 第 16 章 M1 目标中的每一项都有能力 ID 或 L4 用例作为证据，缺口已补齐。验证：评审文件中的映射表。
- [R2-A05] T13–T22 的验收项全部为 `passing`，或为 `blocked` 且原因在评审文件中被接受。验证：`acceptance.json` 检查输出。
- [R2-A06] 四个审查子代理并行运行且相互独立，各自的范围与输入记录在评审文件中。验证：评审文件内容。
- [R2-A07] 每条审查发现都有核实结论与处理（修复、不同意并给理由、登记到具体任务）。验证：`docs/reviews/R2-findings.md`。
- [R2-A08] 每个修复都附带先失败后通过的回归测试。验证：提交记录与测试输出。
- [R2-A09] W1 检查清单覆盖交付物 5 的五类内容，并逐条列出 Windows 相关的 `blocked` 验收项编号。验证：评审文件内容。
- [R2-A10] 架构第 16 章与第 6.0 节已按实际更新，版本号递增并有修订记录；评审文件开头给出明确结论与进入 M2 的前提条件。验证：文档 diff 与评审文件内容。
- [R2-A11] `npm run verify` 通过。验证：命令输出。
