## 背景与目标

第 11 章的预算是发布门槛（NFR-01），M4 退出标准要求"性能预算全部达标"。之前的任务各自测过一部分（S1、S2、S7、T19、T35），口径不统一，也没有回归门禁。本任务把第 11 章每项指标变成自动化测量：PR 跑冒烟，Nightly 在 macOS 与 Windows 跑完整测量，超出预算或相对基线回归超过 10% 就失败；另做 8 小时长跑内存测试。

完成后，任何一项性能回归都会在 CI 中暴露；macOS 上的实测数据写入性能文档，Windows 基准机数据由 W3 用同一套脚本补齐。

## 交付物

### 1. 指标与测量

统计口径：预算写了分位数的按分位数比较；只写单值的，取 N 次运行的中位数比较（N 写进配置，PR 与 Nightly 分别设定）。跨进程打点用同一时钟源，方法写进性能文档。

| 指标 | 预算 | 自动化测量 | 流水线 |
|---|---|---|---|
| 冷启动到可交互窗口 | ≤ 1.0 s | Playwright 启动打包产物，进程启动到首帧加侧栏数据就绪的打点 | PR + Nightly |
| 打开工作区到 Agent Host 就绪 | ≤ 1.0 s | Core 的计时 span：`open_workspace` 到握手完成并恢复会话 | PR + Nightly |
| PiArc 引入的首 token 额外延迟 | ≤ 50 ms | 同一 mock provider（固定首 token 时延）下，直接调用 Pi SDK 与经 Core 的首个 delta 到达时间之差 | Nightly |
| 主进程内存（含 Core，空闲） | ≤ 120 MB | 空闲稳定后 `getAppMetrics()` 中主进程的内存 | Nightly |
| 渲染进程内存 | ≤ 220 MB | 夹具数据目录：侧栏 100 个会话、打开 1 个含 1,000 条 item 的会话，读 `getAppMetrics()` | Nightly |
| 应用全部进程合计（不含 Agent Host） | ≤ 450 MB | 同上夹具，`getAppMetrics()` 全部进程求和 | Nightly |
| Agent Host 内存（1 个活动会话） | ≤ 150 MB | 跨平台读取 Agent Host 进程 RSS | Nightly |
| 每增加一个活动会话的内存增量 | ≤ 40 MB | 1、2、3 个会话同时运行 mock 回合时 RSS 的增量 | Nightly |
| 8 小时长会话内存增长（稳态后） | ≤ 10% | 长跑测试（交付物 3） | 本机 / 缩短版进 Nightly |
| 流式渲染（100 token/s） | 无 > 50 ms 长任务；帧时间 p99 ≤ 16 ms | 真实链路 + mock provider 以 100 token/s 输出，Chrome tracing 或 PerformanceObserver 采集 | PR（短）+ Nightly |
| 万条 item 的 transcript 滚动 | 60 fps | 1 万条 item 夹具，脚本化滚动，统计帧间隔分位数 | Nightly |
| 会话切换 | 已缓存 ≤ 100 ms；冷加载 1,000 条 ≤ 300 ms | 点击到可见行绘制完成的打点 | PR + Nightly |
| 主进程事件循环延迟 | p99 ≤ 16 ms | 流式与 3 会话并行负载下的 `monitorEventLoopDelay` | PR + Nightly |
| Core 事件到渲染进程 | p95 ≤ 5 ms | Core 批次时间戳到渲染进程接收的打点 | PR + Nightly |
| AHP 往返（小文件 fs 操作） | p95 ≤ 5 ms | 契约测试中对 4 KB 文件 `fs/read` 往返计时 | PR + Nightly |
| 无需用户参与的权限裁决 | p95 ≤ 2 ms | Core 基准测试：代表性规则集 + Bash 命令集调用 `policy/evaluate` | PR + Nightly |
| 终端键入回显额外延迟 | p95 ≤ 5 ms | S7 方法的自动化版本 | Nightly |
| 安装包体积 | ≤ 200 MB | Nightly 打包产物（macOS arm64 DMG、Windows x64 安装包） | Nightly |
| 安装后体积 | ≤ 450 MB | `.app` 目录与 Windows 安装目录（或解包目录，口径写明） | Nightly |
| 空闲 CPU | 接近 0% | 窗口可见空闲与隐藏两种状态下 60 秒各进程 CPU 时间；隐藏时断言无 rAF 回调、终端无帧 | Nightly |
| Agent Host 崩溃后恢复 | ≤ 3 s | 故障注入：杀进程到会话恢复可用 | Nightly |
| 渲染进程崩溃或重载后恢复 | ≤ 2 s，会话不中断 | 故障注入：崩溃或重载到 transcript 可见，同时 mock 回合继续 | Nightly |
| Beta 期无崩溃会话率 | ≥ 99.5% | 不进 CI（见"不做"） | — |

- "接近 0%"在本任务中定成具体阈值：依据实测写入第 11 章，并在修订记录中说明。
- 覆盖检查：脚本读取架构第 11 章表格与测量配置，第 11 章每一行都要有对应测量或明确的排除理由，否则失败。

### 2. 门禁与流水线

- 每项测量有两道判定：超出第 11 章的绝对预算；相对基线回归超过 10%。失败输出写明指标、预算、基线值、当前值与运行次数。
- 第 11 章预算以基准机型为准，CI runner 与基准机不同：绝对预算的达标结论来自基准机（或注明配置的本机）实测；CI 上做回归比较。基线按平台与机器类别分别入库，更新基线必须是显式命令，提交说明写明原因。
- PR 流水线跑冒烟子集（上表标 PR 的项），多次运行取中位数；Nightly 在 macOS 与 Windows 跑全部项与缩短版长跑。
- 测量脚本用 Node 编写，跨平台；入口命令写进根 `CLAUDE.md` 的"命令"一节。

### 3. 长跑内存测试

- 负载：mock 会话按固定节奏持续产生回合（含工具调用、文件改动、后台任务与终端输出），同时保持一个窗口打开。
- 稳态：前 30 分钟为预热，之后每 10 分钟采样主进程、渲染进程、Agent Host 的内存；增长率 =（结束值 − 稳态起点值）/ 稳态起点值，三者分别判定。
- 托管 runner 的单 job 时长有上限（实现时查阅），完整 8 小时在本机或自托管 runner 运行；Nightly 跑缩短版（例如 1 小时）做趋势监控。

### 4. 性能文档与预算校准

- `docs/engineering/performance.md`：每项指标的测量方法与口径、运行命令、基线更新流程、macOS 实测数据（机型、系统版本、数值、运行次数），以及留给 W3 的 Windows 一节。
- 实测优于预算较多的项可以收紧：更新第 11 章、递增架构版本号、写修订记录。不达标的项不放宽（放宽属于变更型），登记到 PLAN 并在报告中列为风险。

## 实现要点

- 复用已有的测量代码与夹具，统一到一个测量框架下，不保留多套口径。
- 测量前固定环境：关闭开发者工具、固定窗口尺寸、预热一次；macOS 上记录是否接电源。
- 噪声控制：先在同一提交上连续跑几轮冒烟，确认无误报再接入门禁；噪声过大的指标只放 Nightly，并在文档中说明。
- 演示回归门禁时用临时修改（例如在事件转发路径加入延迟），演示后撤销。
