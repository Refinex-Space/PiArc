## 执行要求

开工前完整阅读 `docs/plan/protocol.md` 并严格遵守。开工检查、范围与决策分级、质量门禁、验收记录、收尾与报告格式都以它为准。最重要的几条：

- 先读后写；外部 API 以锁定版本为准，Pi 的读法见 `docs/plan/references.md`。
- 只做本任务范围内的事；补充型决策自己定，变更型决策写 ADR 提议后停止受影响部分。
- clean-room：参考仓库只学行为，不复制 claude-code 与 OpenClaudeDesktop 生成组件的任何代码、提示词和品牌资产（ADR-0006）。
- 不删改测试和验收项；只有亲自验证通过的验收项才能标 `passing`。
- 每完成一个检查项就更新 `PLAN.md` 检查点并提交；上下文会被自动压缩，不要提前停下。
- 不推送，不打印凭据。

## 背景与目标

M2 交付了 Harness 的核心：完整权限与 Bash 分析、Claude Code 配置兼容、hooks、plan 模式与任务清单、上下文工程、检查点与回退、WebFetch 与登录，以及 L3 对齐基座（T23–T30）。W1 在 Windows 上补齐了 M1。

第 16 章的 M2 退出标准有两条：第 6 章的 M2 能力全部有场景覆盖；L3 对齐在权限与 hooks 上没有未解释的差异。本任务逐条取证，并用四个相互独立的只读审查找出实现中的问题，逐条核实与处理，最后给出 M2（macOS）是否达标的结论。

## 必读

1. 架构设计：第 16 章（M2 目标与退出标准）、第 6.0 节能力矩阵、第 6.1.4 节工具清单、第 6.15 节、第 18 章（里程碑结束时的文档更新）。
2. `docs/plan/acceptance.json` 中 T23–T30 与 W1 的验收项；`PLAN.md` 中 M2 的会话日志与登记事项。
3. `docs/reviews/R2-findings.md`（上次评审遗留项）、`docs/reviews/W1-windows-m1-parity.md`。
4. `tests/capabilities.yaml`、`docs/product/capabilities.md`、`tests/l3-allowlist.yaml`，以及 T30 的 L3 命令与报告格式。

## 范围

### 要做

- 按 M2 退出标准取证：能力覆盖、L3 结果。
- 四个独立只读审查，逐条核实发现并处理。
- 确认 W1 结论；清理登记事项。
- 更新架构文档（第 16 章状态、第 6.0 节矩阵、第 6.15 节校准值）。
- 写 `docs/reviews/R3-findings.md`，给出结论。

### 不做

- M3 功能。审查中发现的、属于后续任务范围的缺口登记给对应任务，不在本任务实现。
- Windows 上的 M2 验收（W2）。本任务只给出 W2 需要重点核对的项。

## 交付物

### 1. 能力覆盖

- 列出 M2 能力清单：第 6.0 节中里程碑含 M2 的行、第 6.1.4 节中 M2 的工具，以及第 16 章 M2 目标中的每一项（完整权限规则与 Bash 分析、plan 模式、任务清单、AskUserQuestion、hooks、checkpoint 与 rewind、压缩与上下文用量、WebFetch、Changes 面板、memory 文件兼容）。
- 映射表：M2 能力 → 能力 ID → 覆盖它的场景文件。没有能力 ID 或没有场景的能力即为缺口：属于 M2 的在本任务补场景或修复，确实不属于 M2 的写明理由。
- 重新生成 `docs/product/capabilities.md`，确认没有 MISSING；运行 `node scripts/plan/check-capabilities.mjs --milestone M2`，确认里程碑不晚于 M2 的能力没有仍为 `planned` 的（`blocked` 的逐条说明）。

### 2. L3 结果

- 运行 T30 的 L3 命令，报告首行的两侧版本写入评审文件。
- 权限与 hooks 场景没有未解释的差异；逐条复核 allowlist 中的理由是否成立，不成立的改为修复或登记。

### 3. 独立审查

并行启动四个相互独立的只读审查子代理（只读、不改文件）。每个审查者拿到的是审查范围、相关文件、架构章节与威胁模型，不给出你的预判：

| 审查 | 范围 |
|---|---|
| 权限与 hooks 安全 | piarc-policy、piarc-hooks、piarc-config；裁决顺序、hooks allow 不越过 deny/ask、项目信任闸门、不写 `.claude/`、Bash 分析的绕过方式、进程树终止、审计完整性 |
| 回退与数据完整性 | piarc-checkpoint、piarc-fs 写入路径、Changes 面板的丢弃；快照与索引的写入顺序、冲突检测、清理是否误删、保真写入、对话分支不改写 JSONL |
| 上下文工程与缓存 | system prompt 组装、reminder 通道、压缩阈值与熔断、重注入上限、缓存断点、plan 模式工具集变化对缓存的影响、提示词原创性 |
| 工程质量 | crate 依赖规则、错误类型化、函数与文件长度、测试纪律（场景名与断言一致、无静默通过）、CLAUDE.md 与代码一致、通用能力复用表 |

### 4. 发现处理

- 每条发现逐条核实：能复现的写失败测试再修复；不同意的写理由；属于后续任务的登记。
- `docs/reviews/R3-findings.md` 按 `docs/reviews/README.md` 的格式记录每条发现：编号、维度、文件与行号、失败场景、核实结论、处理。

### 5. W1 确认与登记事项

- 确认 W1 在看板中为"已完成"，其报告逐条覆盖 M1 退出标准；W1 列出的、需要用户更新的 T13–T22 验收项已在评审文件中汇总。
- 逐条处理 `PLAN.md`"登记事项"：已解决的关闭，仍有效的指定处理任务，不再相关的写明理由后关闭。

### 6. 文档与结论

- 架构文档：第 16 章标注 M2（macOS）状态，第 6.0 节矩阵与实现一致，第 6.15 节数值与代码常量一致；递增版本号并写修订记录。
- 结论写在评审文件开头：M2（macOS）是否达标、进入 M3 的前提条件、W2 需要重点核对的项（来自本次审查与 M2 的平台相关改动）。

## 实现要点

- 审查子代理之间互不可见，避免结论趋同；你只在汇总时比对重复项。
- 修复审查发现时遵守原任务的范围与验收项，不顺手重构；修复后跑受影响 crate 或包的测试，收尾时跑一次全量 verify。
- 发现若需要改变架构或 ADR 的既定内容，按变更型决策写 ADR 提议，并在结论中列为前提条件。
